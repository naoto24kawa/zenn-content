mizchi さんが [sprawlens](https://github.com/mizchi/sprawlens) というツールを公開していた。Git 履歴からコミットごとの import グラフをスナップショットとして集めて、コードベースの「構造の成長」を観測するツールらしい。

目を引いたのは、AI 関与コミットをマーキングする機能が最初から入っていたこと。「AI にコードを書かせるようになって、リポジトリがどう太っていくか」を測ろうとしている道具に見えた。自分も日常的に Claude Code にコードを書かせているので、これは他人事ではない。

気になったので、自分が個人開発しているアプリ（約11万 LOC / 1,495 コミット）に実際に走らせてみた。やってみたら想像以上に面白く、調べていくと裏に半世紀分の研究の蓄積があることも分かったので、まとめて書く。

:::message
本記事の情報は執筆時点（2026年6月）のものです。sprawlens は開発初期のツールのため、CLI インターフェース・出力フォーマット・UI はこの後変わる可能性があります。
:::

## sprawlens とは何か

正式名称は CodeSprawl Lens。TypeScript/JavaScript の import グラフをコミットごとに収集し、構造メトリクスと差分を計算して、タイムライン・ツリーマップ・依存差分・ホットスポットを Web UI で見せる。

mizchi さんの設計で特に良いと思った点が3つある。

1. **git worktree ベースで履歴を収集する**ので、作業ツリーを checkout で汚さない
2. **AI 関与コミットのヒューリスティックなマーキング**が組み込まれている
3. 出力が素の JSON/CSV なので、UI を使わず自前スクリプトや CI からも扱える

[デモ](https://mizchi.github.io/sprawlens/)では sprawlens 自身のコードベースが見られる。

## やってみた: 1ヶ月分・50コミットを健康診断する

直近50コミット（2026-05-04〜06-03）を collect / analyze して、`metrics.csv` を集計した。

| 指標 | 5/4 | 6/3 | 変化 |
|---|---|---|---|
| LOC | 106,481 | 109,878 | +3,397 (+3.2%) |
| ファイル数 | 630 | 635 | +5 |
| import エッジ数 | 987 | 991 | +4 |
| エッジ密度 (edges/file) | 1.57 | 1.56 | ほぼ横ばい |
| 循環依存 | 1 | 1 | 増えていない |
| 最大連結成分 | 181 | 181 | 変化なし |
| max fan-in / fan-out | 66 / 45 | 66 / 45 | 変化なし |
| AI 関与コミット判定 | — | — | 35/50 (70%) |

補足: `import エッジ数` はファイル間 import の総本数。`エッジ密度` は1ファイルあたりの平均 import 本数。`最大連結成分` はあるファイルから辿れる最大のファイル群のサイズ（全ファイル数に近づくほど一枚岩化のサイン）。`AI 関与コミット判定` は「Co-authored-by」「🤖」等のコミットメッセージパターンからヒューリスティックに推定した数。

コミットの70%が AI 関与と判定されている中で、LOC が3.2%増えても構造指標は全部横ばいだった。あくまで1リポジトリ・1ヶ月の観測だが、一応の安心材料にはなった。

### 双方向ハブの特定

「ファンイン」とは、どれだけ多くのファイルから依存されているかの数。上位はこうなった。

| fan-in | ファイル |
|---|---|
| 66 | `api/index.ts`（エントリポイント） |
| 64 | `api/env.ts`（環境変数） |
| 63 | `api/tests/helpers/mock.ts`（テストヘルパー） |
| 32 | `api/types.ts`（共有型定義） |

エントリポイントは依存する数（ファンアウト）も45で最大。依存される側とする側の両方でトップという「双方向ハブ」だった。Hono アプリの典型構造なので「重要なファイルだろう」とは思っていたが、fan-in 66 という数字で影響範囲がリポジトリ内で最大だと初めて確定した。体感を数字に変換できたのが sprawlens の収穫だった。

### どう読むのか — 正常と異常の境目

「循環1って多いのか少ないのか?」と最初は戸惑った。結論から言うと、これらの指標に普遍的な「正常値」はない。意味を持つのはトレンドで、見るべきは「コードの増加率に対して構造の複雑さがどう動いたか」だ。

- **正常**: コードは増えるが、エッジ密度・循環数・最大連結成分は横ばい
- **異常**: コードの増加率を構造指標の増加率が上回る。書けば書くほど絡まっていく状態

今回の診断結果は「全指標横ばい = 健全」、要観察は3つのハブファイル、軽い宿題が i18n の循環、と読める。

## 調べたら50年の歴史があった

実測結果が出たところで、「そもそもこの測り方は誰が考えたんだろう」と気になって調べてみた。するとソフトウェアメトリクスという確立した研究分野の系譜にきれいに乗っていることが分かった。

1970年代に Lehman が「進化するシステムは、手を打たない限り複雑性が単調増加する」という法則を提唱した。つまりさっきの「横ばい」は自然状態ではなく、リファクタリングという逆向きの仕事が行われている証拠として読める。自分のリポジトリが AI 関与70%でも横ばいを維持できていたのは、レビューで構造を守り続けていた効果だと解釈している。

その後 1990〜2000 年代にかけて、ファンイン/ファンアウトによる結合度の定式化、Git 履歴から品質を予測する研究分野（MSR: Mining Software Repositories）、「複雑度 × 変更頻度」でレビュー資源を集中させるホットスポット分析、と積み重なっていった。

つまり理論は半世紀かけて積み上がっていて、mizchi さんが sprawlens で持ち込んだ新しさはツールの技術そのものではなく、「**AI 関与コミットを区別して観測する**」という問いのほうだった。

## これから AI を使う上で有用そうな理由

自分の観測では「AI が書いても構造は保たれた」という結果が出た。ではこれは個人的な幸運なのか、それとも広く言えることなのか。ちょうどその問いを考えさせるデータがある。

GitClear の調査では、AI アシスタント普及後にコピペされたコードの比率が2021年の8.3%から2024年の12.3%へ増加し、リファクタリング率は約24%から10%未満に下がった。一方 DORA（DevOps Research and Assessment、開発生産性の大規模年次調査）では回答者の59%が「AI で品質が上がった」と答えている。**客観メトリクスと主観の乖離**が起きている。

この乖離の原因は diff レビューの死角にある。diff レビューが検証できるのは「この変更が局所的に正しいか」まで。重複コードが複数箇所に生える、依存の向きが崩れる、ハブが肥大化する——そういう大域的な劣化は、書いた本人の体感でも diff でも捉えられない。AI の生成速度が上がるほど、この死角は広がる。

だから、主観でも diff でもない第三の計器が要る。sprawlens はその一つの答えだと思う。

## まとめ

- mizchi さんの sprawlens は、コミット毎の import グラフスナップショットで「コードの大きさと絡まり具合を、時間軸つきで撮るカメラ」だった
- 11万 LOC のリポジトリで実測したら、AI 関与コミット70%でも構造指標は横ばい。「横ばい」は自然状態ではなく、レビューで構造を守る仕事が機能している証拠と読めた
- 裏には半世紀分の研究蓄積がある。新しいのは「AI 関与コミットを区別して観測する」という問い
- AI で開発速度が上がるほど、diff レビューとは別に構造を観測する計器が標準装備になっていく気がしている

公開から日が浅いツールで API も UI もまだ変わっていくと思うが、発想ごと持っておく価値があると思う。
